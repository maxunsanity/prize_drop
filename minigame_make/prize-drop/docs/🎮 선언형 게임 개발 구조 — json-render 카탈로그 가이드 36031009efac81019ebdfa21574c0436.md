# 🎮 선언형 게임 개발 구조 — json-render 카탈로그 가이드

## 핵심 목표

재료(Catalog)와 조리책([GAME.md](http://GAME.md))이 고정되면 어떤 AI든 같은 방향으로 만든다.

커서, GPT, 클로드 — 요리사가 달라져도 재료 목록과 레시피가 있으면 구조 이탈(드리프트)을 막을 수 있다.

단, "픽셀 단위 동일 결과물"이 목표가 아니라 **재작업 비용·버그 반복을 줄이는 것**이 목표다.

## 1. json-render란

json-render는 Vercel Labs의 Generative UI 프레임워크. AI가 UI를 생성할 때 카탈로그에 정의된 컴포넌트만 쓰도록 제한하는 구조.

### 주방 비유

| 용어 | 비유 | 역할 |
| --- | --- | --- |
| Catalog | 메뉴판 | 쓸 수 있는 재료 목록. 이 목록 밖은 못 만듦 |
| Spec | 주문서 | 이번에 뭘 만들지 재료를 골라 적은 주문 |
| State | 값 상자 | 화면에 표시할 실시간 값. $state 경로로 가져옴 |
| Runtime | 주방 | 실제 게임이 돌아가는 곳. Three.js 루프, 충돌, 물리 |

### 3가지 카탈로그 비교 — 형식은 같고 내용만 다르다

| 종류 | type 이름 예시 | 목적 |
| --- | --- | --- |
| 공식 웹 UI | Button, Card, Table... | 범용 UI 컴포넌트 41개 |
| R3F 3D 씬 | Group, Stars, AmbientLight... | 3D 씬 그래프 노드 |
| 게임 전용 | HudCoinBlock, LobbyHeroTitle... | 게임 씬 구성품 |

세 가지 모두 `defineCatalog() + Zod + 컴포넌트별 props 패턴이 동일`. 이름만 다를 뿐 구조는 같다.

## 2. 4레이어 구조

위로 갈수록 사람·AI가 설정, 아래로 갈수록 코드가 실행. 게임 코어(Three.js)는 성능을 위해 명령형으로 유지.

| # | 레이어 | 비유 | 담당 파일 | 성격 |
| --- | --- | --- | --- | --- |
| ① | Catalog | 메뉴판 | catalog.ts, operationalUi.ts, stubsAndMaterials.ts, shared.ts | 선언형 |
| ② | Spec | 주문서 | [GAME.md](http://GAME.md), data/*.json, assembleSpec(), registry.tsx | 선언형 |
| ③ | State / Bridge | 서빙 | hudExternalStore, gameControlBridge | 연결 |
| ④ | Runtime | 주방 | GameCore.ts, Three.js, bootstrapGame, loadGameData | 명령형 |

### 선언형으로 올라온 것 vs 명령형으로 남은 것

**✅ 선언형**

- 로비 카피 UI
- HUD 수치·라벨 ($state)
- CSV 경로 (Catalog Zod literal)
- 버튼 액션
- 부팅 검증 (catalog.validate)

**⚙️ 명령형 (의도적 유지)**

- Three.js 게임 루프 전체
- 스폰·충돌·물리 본체
- 페이즈 전환 로직
- 엔티티 라이프사이클

### 실제 코드 — Spec 트리

```tsx
// playHudSpec — HUD 주문서
{
  root: 'jrRoot',
  elements: {
    coinEl: {
      type: 'RunnerHudCoinBlock',  // 카탈로그에 등록된 이름 그대로
      props: {
        coinPrefix: { $state: '/hud/lblCoinPrefix' },  // State 상자에서 꺼내오는 값
        value: { $state: '/hud/coinStr' },
      },
    },
  }
}
```

### 실제 코드 — Registry 매핑

```tsx
// type 문자열 → React 컴포넌트 연결
const registry = {
  'RunnerHudCoinBlock':    (p) => <HudCoinBlockImpl {...p} />,
  'RunnerHudScoreStack':   (p) => <HudScoreStackImpl {...p} />,
  'RunnerHudTimerStrip':   (p) => <HudTimerStripImpl {...p} />,
  'RunnerHudInvincRibbon': (p) => <HudInvincRibbonImpl {...p} />,
};

// Renderer가 Spec을 읽고 registry로 화면에 그린다
<Renderer spec={playHudSpec} registry={registry} />
```

**Spec은 데이터, 화면은 registry가 연결.** registry는 한 번 만들면 재사용.

## 3. 카탈로그란

**카탈로그 = 이 씬에 존재할 수 있는 구성품 이름 목록.**

값 없음. 규칙 없음. 존재 선언만.

| ❌ 카탈로그에 넣지 않는 것 | ✅ 카탈로그에 넣는 것 |
| --- | --- |
| 색상, 크기, 폰트 등 UI 값 | Wheel — 존재 선언 |
| weight, cost 등 게임 규칙 | SpinButton — 존재 선언 |
| 회전 시간, 바운스 등 연출 값 | TokenDisplay — 존재 선언 |
| weightedRandom() 등 로직 | DataMaterial_* — CSV 경로 리터럴 |
| 카메라 위치, 조명 강도 | bindsTo (element 참조용) |

---

## 4. 카탈로그 컴포넌트 선정 기준 (7가지)

운영 UI 카탈로그(`operationalUi.ts`)에 올리려면:

1. **선언 레이어 경계** — Three 루프·충돌·스폰·페이즈 본체는 올리지 않는다. DOM 오버레이(HUD·로비 카피·버튼)만 후보.
2. **Spec으로 말 가능한가** — type/props/children/visible 패턴으로 조립 가능한가. 동적 값은 $state와 짝을 이룬다.
3. **한 컴포넌트 = 한 UI 의미** — 작은 블록 여러 개가 유지보수에 유리. "로비 전체"가 아니라 "로비 제목" 단위.
4. **이름 규칙** — 재료는 `DataMaterial_*`. 화면 부품은 `Hud*`, `Lobby*` 등.
5. **Zod props 좁게** — 재료는 좁은 리터럴. HUD 동적 필드는 `hudBindProp`. z.any() 금지.
6. **registry 세트** — 운영 타입은 registry JSX와 **같은 패치**로 추가. 카탈로그에만 있고 registry 없으면 → stubs 쪽.
7. **액션은 얇게** — 버튼 한 번에 코어 메서드 한 번. 복잡한 로직은 명령형·CSV 쪽.

### 스텁 → 운영 UI 승격 기준

"화면에 진짜로 띄운다고 결정하는 순간" → 7가지 기준 전부 만족 + registry JSX 같은 패치.

## 5. 파일 4개 분리 이유

| 파일 | 역할 | 약속 |
| --- | --- | --- |
| `catalog.ts` | 관문. defineCatalog() 한 번으로 단일 인스턴스 | 외부는 이 파일만 import |
| `operationalUi.ts` | 실제 화면에 그려지는 컴포넌트만 | 여기 있는 것 = 화면에 나온다 |
| `stubsAndMaterials.ts` | 재료(CSV 경로) + 스텁(개념 이름만) | 여기 있어도 화면에 안 나온다 |
| `shared.ts` | hudBindProp 등 공통 Zod 조각 | 규칙 바꿀 때 이 파일 하나만 |

**한 파일에 다 넣으면 생기는 문제:** "카탈로그에 이름이 있으니까 구현된 줄 알았다" → registry 없음 버그.

### hudBindProp

```tsx
hudBindProp = z.union([
  { $state: "/hud/…" },  // /hud/로 시작하는 경로만 (엄격)
  string, number, boolean  // 초기값·라벨용 (느슨하게)
])
```

HUD에는 고정 텍스트 라벨이 많아서 전부 $state 강제는 과도함. 이 정도가 적절한 타협.

## 6. 데이터 파이프라인 & SSoT

**SSoT 원칙:** 데이터 경로는 반드시 한 곳에서만 관리. 경로 하나 바꾸면 Catalog Zod literal + 레지스트리 + 연구 Spec을 **동시에 패치**.

```
CSV / JSON → 경로 단일 관리 → Zod 검증 → assembleSpec() → Registry → 화면
```

### 데이터 계층 분리

| 구분 | Spec에 들어가는 것 | 담당 |
| --- | --- | --- |
| 게임 계약 | weight, reward_type, cost | sections.json, spin-rules.json |
| UI 크롬 | 배경색, 휠 크기 | ui-config.json |
| 표현 레이어 | 카메라 FOV, 조명 강도 | presentation.json |
| 데이터 재료 | CSV 경로 리터럴 | stubsAndMaterials.ts |

### 연구 Phase 진행 상태

| Phase | 상태 | 내용 |
| --- | --- | --- |
| Phase 1 | ✅ 완료 | CSV 경로 드리프트 방지. DEV 불일치 시 즉시 throw |
| Phase 2 | ✅ 완료 | 부팅 시 catalog.validate(spec) 실행 |
| Phase 3 | 🔶 진행 중 | 로더 출력 ↔ 선언층 완전 대칭 |
| Phase 4 | ⏸ 미착수 | 외부 패치 → Catalog 검증 거절 |

## 7. 세트 수정 규칙

> 가장 자주 깨지는 패턴: 한 곳만 수정하고 나머지를 빠뜨리는 것.
> 

**HUD $state 경로 수정 시 — 반드시 3곳 동시**

`hudExternalStore 경로` + `Spec $state 문자열` + `pushHudChrome 키`

**CSV 경로 수정 시 — 반드시 동시 패치**

`runnerDataPaths.ts` + `Catalog Zod literal` + `연구 Spec`

**운영 UI 새 타입 추가 시**

`operationalUi.ts 타입 추가` + `registry JSX 구현` → 같은 패치

**카탈로그 액션 이름 수정 시**

actions 키 문자열과 overlayActionHandlers 키 문자열 완전 일치 필수. 불일치 시 버튼 무동작.

**visible 필드 누락**

DEV 검증 켠 상태에서 visible 누락 → catalog.validate 실패 → 앱 진입 차단. 모든 element에 `visible: true` 필수.

## 8. 제작 순서

### 두 문서 역할 분리

| 문서 | 역할 |
| --- | --- |
| [GAME.md](http://GAME.md) | 게임 의도·DOM·금지·SSoT·json-render 경계 (헌법) |
| JSON_RENDER_[Guide.md](http://Guide.md) | 카탈로그·Spec·재료·폴더 지도·연구·제작 순서 (실무 가이드) |

구조 바꾸면 **두 파일 모두 업데이트**.

### 제작 단계

1. **한 판 루프 정의** — 페이즈·입력·보상을 한 줄로. [GAME.md](http://GAME.md) 작성 시작.
2. **데이터화할 것 결정** — 자주 손댈 것을 CSV/JSON으로. 시트 하나 = 한 책임. 초기 과분할 금지.
3. **카탈로그 구성품 나열** — 존재 선언만. §4 선정 기준 적용해서 operationalUi vs stubs 분류.
4. **CSV 경로 SSoT 세팅** — 경로 상수 파일 먼저. Catalog Zod literal + 레지스트리 동시 연결.
5. **data/*.json 작성** — sections, spin-rules, player-defaults, ui-config, presentation 역할별 분리.
6. **registry.tsx 구현** — type → React 컴포넌트 매핑. 운영 UI 추가할 때 카탈로그 + registry 동시 패치.
7. **개발자에게 전달** — `assembleSpec()` + `<GameExperience spec={spec} />` 두 줄만.

### 다른 장르로 이식할 때

**이식 가능:** 경로 SSoT + 시트 재료 패턴 / 선언 가능 UI / DEV 정합 검증 / 세트 수정 규칙 / 파일 4개 분리 패턴

**무조건 갈아야:** 플레이 코어 클래스 / 각 시트 컬럼 스키마 / 카탈로그 타입 이름 / registry JSX / [GAME.md](http://GAME.md) 전체

## 9. 현재 한계

| 구역 | 상태 | 비고 |
| --- | --- | --- |
| 로비 라디오 버튼 | 하이브리드 | 아직 HTML + 명령형 |

**정확한 현재 상태:**

- ✅ UI + 데이터 선언화 — 로비·HUD·CSV 경로·버튼 액션

- ✅ 버그 누적 방지 — Anti-Patterns + 세트 수정 규칙
- 🔶 하이브리드 상태 — UI 일부는 아직 HTML+명령형
- 🔜 장기 목표 — 게임 월드 전체 선언형 (Three 코어는 명령형 유지)
