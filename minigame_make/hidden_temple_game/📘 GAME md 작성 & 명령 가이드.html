📘 GAME.md 작성 & 명령 가이드

이 문서는 GAME.md를 작성할 때와 AI에게 구현을 지시할 때의 표준 가이드야.
새 게임을 만들 때마다 이 문서를 참조해서 일관된 품질을 유지해.

1. 표준 섹션 구조 (모든 게임 공통)

모든 GAME.md는 아래 구조를 반드시 따라야 해:

YAML front matter
├── identity
├── implementation    ← 파일 구조 (게임마다 명시)
├── components
├── entities
├── mechanics         ← actions + loops
└── goals

## Design Pillars     ← 핵심 설계 원칙 (3~5개)
## User Flow          ← 플레이어 행동 흐름 (필수)
## Mechanics in Depth ← 구현 세부 규칙
## Content Guidelines ← 데이터 추가/수정 방법
## Anti-Patterns      ← [CRITICAL] 버그 방지 목록

작성 원칙

  • components는 평탄하고 단순하게 — chess.md 수준
  • implementation.files에 각 파일의 역할을 한 줄로 명시
  • data_files에 CSV 파일 목록 포함
  • Anti-Patterns는 [CRITICAL] 태그 + 이유 한 줄 필수

2. User Flow — 별도 강조

왜 필수인가

User Flow가 없으면 AI가 아래 항목들을 임의로 결정해:

  • 화면 전환 순서
  • 모달/팝업이 뜨는 시점
  • ANI ID가 어느 순간에 실행되는지
  • 소진 같은 예외 상황 처리

User Flow가 있으면:

  • AI가 화면 흐름을 정확히 이해
  • 개발자가 기획 의도를 바로 파악
  • 모달 자동 진행 같은 오류 사전 방지

작성 방법

## User Flow

### 1. [단계명]
트리거 이벤트
  → 화면/팝업 ID
  → 플레이어 행동
  → 다음 단계
      ├── 분기 A → 결과 A
      └── 분기 B → 결과 B

규칙

  • 단계마다 번호 부여 (1. 진입 / 2. 메인 게임 / 3. 클리어 등)
  • 화살표(→)로 흐름 표현
  • 분기는 들여쓰기 + ├── / └──
  • 각 단계에서 실행되는 ANI ID 명시
  • 예외 흐름 (소진, 타임아웃 등) 반드시 포함

예시 (Hidden Temple 기준)

### 1. 진입
이벤트 배너 탭
  → HT-UI-001 진입 팝업
  → "발굴 시작" 탭
  → HT-UI-002 메인 게임 화면

### 2. 메인 게임
타일 탭
  → HT-ANI-001 곡괭이 스윙
  → HT-ANI-002 타일 파괴
  → 내용물 판정:
      GEM          → gems_collected +1, HT-ANI-006
      ITEM         → 마지막 조각 → item_collect 시퀀스
      EMPTY_REWARD → 소량 보상, HT-ANI-006
      EMPTY        → 먼지 효과만

### 3. 아이템 발굴
마지막 아이템 조각 파괴
  → HT-ANI-003: 아이템 중심 팝업 (0.5초 대기)
  → HT-ANI-004: 이모지 rotate(360°) → 슬롯 비행 0.8s
  → 슬롯 filled = true → check_stage_clear()

### 4. 스테이지 클리어
active_items.every(filled) == true
  → HT-ANI-005: 슬롯 아이템 → Door 비행
  → #stage-clear-modal 표시 (자동 진행 금지)
  → 플레이어 탭 → 다음 스테이지

### 5. 예외: 소진
pickaxe_count == 0
  → 충전 유도 팝업
  → board_state 완전 보존 (리셋 절대 금지)
  → 복귀 시 resume() → 이어서 진행

3. AI 구현 명령 템플릿

기본 명령 (한 번의 명령으로 구현)

GAME_[게임명].md 파일은 게임 기획서 포맷이야.
이걸 자세히 읽고 게임을 제작하는데
관련 csv도 첨부해 놓았으니깐
찬찬히 아주 자세히 살펴 보면서 만들어야 돼.

특히 Anti-Patterns 섹션에 명시된 버그들은
반드시 사전에 방지하면서 구현해줘.
구현 완료 후 아래 순서로 직접 테스트하고 결과를 보고해줘:

1. 게임 실행 → 첫 화면이 정상 표시되는가
2. 핵심 입력 → [게임 핵심 동작]이 실행되는가
3. 보상 연출 → 아이템/보상 애니메이션이 실행되는가
4. 단계 전환 → 클리어 모달이 뜨고 다음 단계로 넘어가는가
5. 예외 처리 → 재화 소진 시 진행 동결되고 리셋되지 않는가

위 5가지 중 하나라도 동작하지 않으면
완료 선언하지 말고 즉시 수정해줘.
그리고 Anti-Patterns 항목을 하나씩 체크해서 보고해줘.

핵심 포인트

  • "자세히 읽고" → AI가 파일을 제대로 파악하게 유도
  • "csv도 첨부" → 데이터 파일까지 함께 읽게 유도
  • "직접 테스트" → 완료 선언 전 자가 검증 강제
  • "Anti-Patterns 체크 보고" → 알려진 버그 사전 방지 확인

4. 품질 체크리스트

GAME.md 작성 완료 후 아래 항목 확인:

  • implementation 섹션이 YAML 안에 있는가
  • User Flow 섹션이 있는가
  • 각 User Flow 단계에 ANI ID가 명시됐는가
  • 예외 흐름이 User Flow에 포함됐는가
  • AI가 임의로 만들 수 있는 항목(이모지 매핑 등)이 명시됐는가
  • Anti-Patterns에 [CRITICAL] 항목이 4개 이상인가
  • 수치값(색상코드, 좌표값 등)이 구체적으로 명시됐는가
  • 모든 ANI에 지속 시간(ms)이 명시됐는가
  • 파티클/카메라 효과에 수치가 명시됐는가
  • DOM element ID 테이블이 있는가
  • Animation Specifications 표가 있는가
  • LocalStorage Schema가 있는가
  • CSV 파싱 주의사항이 Content Guidelines에 있는가
  • 디버그 버튼(#reset-btn 등)이 명시됐는가
  • 게임별 테스트 항목 5개가 명령에 포함됐는가

5. 공통 버그 목록

모든 게임에서 반복되는 버그들. Anti-Patterns에 반드시 포함:

  • index.html에 게임 로직 — 마운트 포인트만. 모든 로직은 src/ 하위
  • 단일 파일 구현 — 절대 금지
  • 자동 진행 — 모달 + 플레이어 탭 필수
  • 모바일 viewport — maximum-scale=1.0, user-scalable=no + touch-action: none
  • item_ids CSV 파싱 — "1002,1003" RFC 4180 quoted field. split(',') 금지
  • 소진 시 리셋 — 재화 소진은 진행 동결만. 상태 초기화 절대 금지

6. 애니메이션 명세 작성 규칙

왜 수치가 필요한가

추상적인 표현은 AI가 두 가지 방식으로 처리해:

  • 생략 — "어떻게 구현할지 모르겠으니 일단 빼자"
  • 지시 대기 — "기획서에 없으니 확인받겠다"고 작업 중단

둘 다 결과물 품질을 떨어뜨려.

나쁜 예시 vs 좋은 예시

나쁜 예시 (추상적):

HT-ANI-002: tile crack and crumble with dust particles

좋은 예시 (수치 명시):

HT-ANI-002: 타일 파괴
  - 타일 scale 1→0 + opacity 1→0, 300ms ease-out
  - 파티클 8개: 반경 40px 사방으로 튀어나감, 중력 적용, 500ms 후 소멸
  - 카메라 x/z ±2px 랜덤 진동, 6프레임, 200ms

규칙

  • 모든 ANI에 지속 시간(ms) 필수
  • 파티클이 있으면 개수 + 범위 + 소멸 시간 명시
  • 이동 애니메이션은 시작점 → 끝점 + 이징 명시
  • 카메라 효과는 진폭 + 프레임 수 + 지속 시간 명시

7. 구현 검증 (테스트) 규칙

왜 필요한가

AI가 게임이 실제로 동작하지 않는데도 "완성"이라고 선언하는 경우가 있어.

명령에 테스트 항목을 명시하면 완료 선언 전 자가 검증을 강제할 수 있어.

게임별 테스트 항목 예시

Hidden Temple:

1. 게임 실행 → 5×5 보드가 표시되는가
2. 타일 클릭 → 곡괭이가 소모되고 타일이 파괴되는가
3. 아이템 발굴 → 슬롯으로 날아가는 애니메이션이 실행되는가
4. 스테이지 클리어 → 모달이 뜨고 다음 스테이지로 넘어가는가
5. 곡괭이 소진 → 진행이 동결되고 보드가 리셋되지 않는가

Dragon Nest:

1. 게임 실행 → 핀볼 보드와 드래곤이 표시되는가
2. 스프링 발사 → 공이 위로 날아가고 범퍼에 튕기는가
3. 슬롯 착지 → 해당 슬롯이 점등되고 토큰이 계산되는가
4. 게이지 업데이트 → 토큰이 드래곤 게이지에 반영되는가
5. 구슬 소진 → 충전 유도 화면이 뜨고 진행 상태가 유지되는가

규칙

  • 테스트 항목은 게임 핵심 루프 기준으로 5개
  • 항상 예외 처리 (소진/타임아웃) 포함
  • 하나라도 실패하면 완료 선언 금지

8. 모듈 A: Three.js 기반 게임

탐색형/퍼즐형 게임에 추가 적용 (Hidden Temple 등)

추가 Anti-Patterns

  • OrthographicCamera up vector — camera.up.set(0, 0, -1) before lookAt. 미설정 시 모든 클릭이 보드 중앙에만 등록
  • 씬 정리 누락 — 스테이지 전환 시 모든 geometry/material dispose 필수. LineSegments 누락 시 유령 그리드 잔존
  • BoxGeometry 타일 — 반드시 PlaneGeometry. 3D 깊이 절대 금지
  • Hidden 타일 색상 차별 — 모든 hidden 타일은 동일 텍스처. content별 색상 구분 금지

3D 레이어 구조 명시 필수

y =  0.000  Hidden 타일      PlaneGeometry
y =  0.005  Hidden 엣지      EdgesGeometry (LineSegments)
y = -0.005  아이템 텍스처    PlaneGeometry (CanvasTexture)
y = -0.010  구멍 바닥        PlaneGeometry
y = -0.009  구멍 엣지        EdgesGeometry (LineSegments)

9. 모듈 B: 결과값 제어 파이프라인

확률 기반 게임 (핀볼/룰렛/슬롯 등)에 적용.

물리 시뮬레이션으로 연출하지만 결과는 기획자가 제어해야 할 때 사용.

패킷 해킹 방지, 확률 테이블 조정이 필요한 게임에 적용.

3단계 파이프라인

game_1.md          game_2.md              game_3.md
순수 물리 엔진  →  헤드리스 시뮬레이터  →  확률 제어 + 플레이백
(랜덤 물리)        (자동 N회 실행)         (probability_config로 제어)
                        ↓
                 simulation_log.json       ← game_3 궤적 재생용
                 simulation_summary.csv    ← 확률 테이블 보정 참고

game_1.md — 순수 물리 엔진

  • 결과 선결정 없음. Lerp 없음. 완전 랜덤 물리
  • 모든 라운드를 round_log에 기록 (game_2 입력값)
  • 디버그 버튼 필수

game_2.md — 헤드리스 시뮬레이터

  • Matter.Render 없이 headless 실행
  • game_1과 동일한 물리 상수 사용 (다르면 데이터 무효)
  • 슬롯별 목표 횟수 달성까지 자동 실행
  • simulation_log.json + simulation_summary.csv 출력

game_3.md — 확률 제어 + 플레이백

  • probability_config.csv로 슬롯 가중치 제어
  • 발사 전 weighted_random()으로 결과 선결정
  • game_2 로그에서 매칭 궤적을 찾아 애니메이션 재생
  • Lerp 보정: Body.applyForce()만 허용

추가 Anti-Patterns

  • vy 양수 발사 — Matter.js Y축은 아래가 양수. vy = -speed
  • 물리로 결과 결정 — 결과는 항상 weighted_random() 선결정
  • Lerp 스냅 — Body.setPosition() 금지. Body.applyForce()만
  • 봇 고정 간격 — setInterval 금지. 재귀 setTimeout + random()
  • probability_config 가중치 합계 — 반드시 1000

10. 파일 명명 규칙

GAME_[게임명].md           ← 게임 기획서
[prefix]_stage_config.csv  ← 스테이지 설정
[prefix]_item_config.csv   ← 아이템 설정
[prefix]_event_config.csv  ← 이벤트 설정

확률 기반 게임 추가:
[prefix]_slot_config.csv        ← 슬롯 레이아웃
probability_config.csv          ← 확률 가중치 (game_3)
simulation_log.json             ← 시뮬레이터 출력 (game_2)
simulation_summary.csv          ← 슬롯별 통계 (game_2)

예시:

  • GAME_hidden_temple.md + ht_stage_config.csv
  • GAME_dragon_nest.md + dn_slot_config.csv + probability_config.csv

11. 표준 작업 순서

1. 현중 + Claude 대화
   → 게임 기획 상의
   → GAME.md + CSV 파일 완성
   → 이 가이드 체크리스트 확인

2. GAME.md 노션 저장
   → 제작중 게임 폴더에 보관

3. Claude Code / Cursor / 안티그래비티에 전달
   → 기본 명령 템플릿 사용 (테스트 항목 포함)
   → GAME.md + CSV 파일 함께 전달

4. 버그 발견
   → Claude와 분석
   → GAME.md Anti-Patterns 업데이트
   → 재구현

5. 완성
   → 노션 GAME.md 최신 버전으로 업데이트
